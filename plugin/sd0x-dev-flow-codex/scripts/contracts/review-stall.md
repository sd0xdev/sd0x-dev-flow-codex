# Review loop diagnosis

Before diagnosing repeated findings, compare authenticated rounds and exact subjects. Give each finding a stable identity from the affected component, triggering behavior, failure mechanism and obligation, not its line number or wording. Record a compact table of identity, round/fingerprint, evidence, attempted fix and observed result in the active feature request or an explicitly selected durable project note; keep secrets out. Do not copy runtime state into tracked files.

Use the native review-diagnostics module to compare normalized component/trigger/mechanism/obligation identities across distinct round IDs. Its result is advisory and cannot authenticate the input or close a gate. Repeated wording alone is not proof of a stall. Distinguish an unchanged defect, a regression, unsupported reviewer evidence, insufficient tests, stale subject, and infrastructure failure. Read the relevant implementation and reproduce the trigger. Change one failed hypothesis or investigation method, add a discriminating test when warranted, and re-review with the configured primary. Preserve evidence of what changed and whether the next round actually improved it.

Use a fresh configured review round when context is lost; no fallback reviewer, rotation count, round cap or stall note has gate authority. A technical recovery may fix infrastructure without rewriting evidence. Continue independent work; isolate the affected operation when an external dependency or missing authority remains. Report the concrete blocker and durable continuation evidence rather than claiming completion.
