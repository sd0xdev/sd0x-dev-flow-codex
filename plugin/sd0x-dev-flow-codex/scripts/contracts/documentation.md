# Documentation structure and comments

Before splitting a lifecycle document or applying a documentation exemption, resolve its feature and full path through the owning create-request resolver. Canonical 1-requirements.md, 2-tech-spec.md and 3-architecture.md remain stable entrypoints. Move detailed explanations into contained supporting references only when this improves navigation; retain a coherent canonical summary and explicit links. Do not invent source-platform layouts that the native resolver cannot consume.

Preserve existing decisions, request history, attribution, source provenance and user-authored content. ADRs use architecture ADR mode and immutable numbered records; a replacement links both directions and marks the old decision superseded without rewriting its historical rationale. Check inbound/outbound links after a move.

Assess long documents by responsibility and navigability, not line count alone. Generated catalogs, fixed schemas, external specifications, legal/license text and executable examples may require one coherent block. State the functional reason for an exemption and the checks that still apply. Source comment-run thresholds are project guidance, not a new Codex completion gate. When a repository has a comment-block checker, inspect its actual counting units, exclusions and skipped-file conditions before changing it or relying on an exemption; never report a skipped check as pass. Preserve pragmas, license headers and machine-consumed comments.

Documentation review checks claims against code and evidence. A draft must identify unsupported portions. Do not replace measured reads or tokens with file lengths, or treat a migration map as accepted functionality.

The native comment-scan action takes an explicit contained JavaScript/shell file list. It counts logical comment lines across blank bridges; an exempt license/directive covers its initial contiguous run only. It reports 25–29 lines as warning and 30+ as a finding, with no automatic gate authority. An empty file scope is uncovered, never clean. Adopt thresholds as documented project guidance; keep functional exemptions explicit.

## Authority-aware feature context

The owning create-request resolver returns a full shape with scan_error, doc_inventory, four disjoint source sets, canonical_ambiguities and exact intent identity. Files are repository-relative. Reject malformed/partial JSON, missing scan_error and failed reads; an unsuccessful process is unknown, never an empty complete corpus. Recover the failure or isolate only the unsupported claim. Classify every observed file once by Current authority, Design record, Work record or History record. Requests include archived requests; bare feature-root archived directories stay outside the active corpus. Symlinked scan entries are refused.

Only Current authority owes alignment with current code. Frozen Design/Work/History records retain their dated truth, with dated addenda where appropriate. Metadata is recognized only in the initial preamble (at most 30 lines): optional heading, then consecutive quoted bold-key fields. Body text, examples, fences and later headers cannot demote a document. Unknown or conflicting roles fail closed to Current authority; an explicit Yes authority declaration wins, and No can only demote a valid Current authority result. A type override cannot change this independent role decision.

Canonical requirements/spec compatibility aliases remain strings or null. Selection is root exact, exact split main, then one root variant; ambiguity is separate from absence. Consumers selecting design must filter design_records by the desired type first and select the sole entry or unique canonical main within that set. Never restore excluded history through the role-blind alias. Ask, runbook, recap and test-health consumers label Corpus scan: complete or unknown and distinguish present behavior from dated intent/evidence.

The exact intent-<feature>.md is a Design record and is read before feature development, bug fixing, requirement/spec writing and requests. Wrong-key files remain strays. Requirement/spec authors may create an absent intent from accepted planning using the exclusive intent-create operation: at most 60 lines, North star, Non-goals, 3–7 INV-nnn invariants and Acceptance sketch. Existing intent is read-only; update-docs never appends or rewrites it. Cite a conflicting invariant and resolve only the dependent scope through actual user authority. Missing intent is advisory when planning already exists, never an automatic permission checkpoint.
