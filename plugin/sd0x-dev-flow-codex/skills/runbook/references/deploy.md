# Declared deployment mode

Read the active deployment, Git action and project-policy contracts using the installed contract reader. This mode adapts upstream deploy-flow; it is separate from default runbook document work. Resolve the project policy with the native workflow action policy. Missing deploy steps are a configuration gap: inspect the actual local release flow, draft a user-owned declaration if within the request, and preserve any existing settings. A declaration does not authorize deployment.

The installed runner entrypoint workflow/native.js accepts one JSON request. deploy-plan takes an integer index in declared order and optional concrete bindings.source/bindings.target for prefix patterns. It returns HEAD/branch, policy and helper identity, source/target OIDs or tracked executable hash, exact literal argv, effects and plan SHA-256. Never interpolate a shell command or invent a branch from ambiguous candidates; inspect local branches and select the one established by user scope.

Prepare and explain the exact step before any missing scope question. Existing scope remains valid when it covers the action, target and consequences. A run script can commit, push, publish or deploy using existing credentials; inspect its actual behavior and make those effects explicit. run_steps: print only prints the plan; execute does not grant execution scope. Do not pass an execution grant for a preview-only request.

An in-scope execution sends deploy-step with the complete unchanged plan and grant.plan_sha256 bound to it. The grant object only binds the real conversation grant; it cannot create execution scope. Keep execution in the same loaded implementation across branch switches: the helper pins its implementation identity and rejects a changed implementation on the next invocation. For multi-step flows, the loaded deployment module exposes runFlow(root, {authorize, bind}) so each next step is planned after the previous result. The authorize callback must obtain actual in-scope user authority, not return unconditional grants.

Execute declared order only. Stop on decline, nonzero exit, signal, timeout, conflict, declaration/helper drift or readback mismatch. No hidden reset or automatic retry. The helper verifies exact merge parents/message or fast-forward OID; script output is represented by hashes to avoid leaking secrets. Record plan hash, resulting HEAD, executed/printed outcome and reconciliation need in the current task evidence. Independently observe required deployment health within user-authorized scope; process success alone is not production readiness.

After interruption inspect actual local history, declaration and any external effects before preparing remaining steps. Do not replay a step whose effects are unknown. Preserve historical evidence and require fresh concrete authority only where the recovered scope differs. This workflow never writes review/verification state and never changes global Codex configuration.

A local merge is a history-rewrite operation. A declared executable may also perform a commit operation, push operation, pr-write operation or connector-write operation. The exact script effects must be established before execution.
